# 데이터 검수 정책

사용자가 지정한 검수 절차를 PRD 9.1·9.2절, FR-06, NFR-01에 연결한다. 자동화가 검사할 수 있는 원문 존재와 사람이 판단해야 하는 의미적 정합성을 구분한다.

## 1. 초안과 사람 검수

Codex는 실제 확보한 말뭉치에서 질문·근거 후보·답변 초안을 만들 수 있다. 파일과 DB의 최초 상태는 `review_status = draft`다. 미확보 원문·FAQ·해석자료를 확인한 것으로 표시하지 않는다.

사람은 다음 네 항목을 원문과 대조하고 각각 `pass`, `fail`, `uncertain` 중 하나와 사유를 기록한다. 아직 검토하지 않은 항목은 `pending`으로 둔다.

| 항목 | 확인 내용 | 자동화의 역할 |
| --- | --- | --- |
| 존재 / `existence` | 인용 조·항·호와 발췌가 지정 버전의 `provision` 원문에 있는가 | ID·버전·문자열 검사 보조 |
| 의미 / `meaning` | 원문이 답변의 실제 주장을 뒷받침하는가 | 자동 통과 처리하지 않음; 사람이 원문을 읽고 판단 |
| 시점 / `temporal` | 기준일에 해당 버전이 적용되는가, 경과조치가 있는가 | 기간 필터는 보조; 조문별 적용 조건을 사람이 확인 |
| 완전성 / `completeness` | 정의·위임·예외·부칙·별표가 빠지지 않았는가 | 참조 누락 탐지 보조 |

네 항목을 사람이 모두 통과시키고 검수 로그를 남겼을 때만 `reviewed`로 전환한다. 실패·애매함이 남으면 `needs_review`, 원문 자체 미확보 또는 확정 불가능이면 사유와 함께 `excluded`로 둔다. 미검토 초안은 `draft`를 유지한다. 수정한 질문·답변·근거는 이전 검수 결과를 그대로 상속하지 않고 다시 검수한다.

## 2. 검수 기록

다음 구조를 검수 파일/DB에 보존한다. 사례별로 여러 근거를 검토하면 각 `provision_id`를 빠짐없이 연결한다.

- `example_id`, `example_revision` 또는 내용 해시, `provision_ids`, `snapshot_id`
- `reviewer`, `reviewer_role` (`developer` 또는 역할을 명시한 `external`), `review_date`
- `method` (원문 직접 대조, 공식 FAQ 대조, 공식 해석 대조 등), 사용한 공식 자료의 ID/URL
- 네 항목별 결과·사유, 종합 `result`, `external_review`

검수 이력은 누가 언제 어떤 사례·버전을 검토했는지 재현할 수 있어야 한다. Codex가 사람의 이름·검수 일시·통과 결과를 대신 만들어 넣지 않는다. AI 검사 결과는 사람의 검수 로그와 별도로 저장한다.

`reviewed`는 개발자 검수 완료를 포함하는 데이터 상태이며 법률적 정확성의 인증이 아니다. 외부 검토가 있으면 `external_review`와 역할을 분리하고, 모델 카드에는 전체 대상 수·실제 외부 검토 수·비율을 기록한다. 10~20% 무작위 표본 검토는 검토자가 확보되었을 때의 선택안이다.

외부 검토자가 없을 때는 공식 FAQ·해석자료와의 교차 대조를 최소 검수 기준으로 적용한다. 해당 쟁점을 대조할 자료를 확보하지 못하면 이를 임의 면제하거나 AI 판단으로 대체하지 않고 `needs_review` 또는 확정 불가능 사유의 `excluded`로 남긴다. FAQ는 법령과 동일한 효력으로 취급하지 않는다.

## 3. 최종 평가셋 봉인

최종 100문항을 검수한 뒤 개발·학습 자료와 물리적으로 분리된 경로에 저장하고 내용 해시·파일 목록·봉인 시점·검수 요약을 남긴다. 학습·검색 인덱싱 스크립트가 이 경로를 탐색하지 않도록 입력 경로를 분리하고, 가능하면 파일 권한도 분리한다.

최종 평가 질문·정답·해설은 프롬프트 개선·검색 튜닝·학습 자료 생성에 다시 사용하지 않는다. 디버깅 등으로 열람하거나 재사용했으면 이력을 남기고 누출 여부를 판단한다. 해당 결과로 개선했으면 개발 평가셋으로 전환하고 새 최종 평가셋을 준비한다.
