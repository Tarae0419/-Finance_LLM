# FinReg 스프린트 계획 v1.0

**기준 문서:** [PRD v1.0](FinReg_LLM_PRD_v1.md), [FinReg 개발 스킬](../SKILL.md)
**계획 상태:** Sprint 1 진행 중. 작업 시간·데이터 수량·완료 주차는 실측 후 조정한다.
**현재 상태:** API·DB 개발 기반을 구성했다. 티켓별 실제 상태와 검증 결과는 [Sprint 1 진행 기록](Sprint_1_Progress.md)에서 관리한다.
**목표:** 은행 대출상품 설명 관련 법규를 검색하고, 기준일과 근거를 확인하거나 적절히 보류하는 자체 운영 LLM의 내부 데모를 완성한다.

## 1. 일정과 작업량 가정

- 1인 개발, **2주 단위 4개 스프린트**로 구성한다. 시작일이 정해지지 않았으므로 W1~W8은 착수일부터의 상대 주차다.
- 각 스프린트는 **구현·검수 34시간 + 예비·운영 6시간 = 40시간**을 편성한다. 6시간 중 2시간은 계획·중간 점검·데모·회고에, 4시간은 수정·환경 문제 대응에 사용한다.
- 전체 예산은 **160시간**이다. 주 20시간이면 8주, 주 15시간이면 산술상 약 11주가 필요하다. PRD의 주 15~20시간 범위 중 상단을 사용한 8주안이다.
- 추정치는 사람이 작업하는 시간이다. 모델 다운로드·GPU 실행·외부 자료 접근 대기는 별도 경과 시간으로 기록하며, 실행 준비·관찰·결과 분석은 작업 시간에 포함한다.
- 학습 300건을 기본 목표, 500건을 여유가 있을 때의 확장 목표로 둔다. 검수 속도를 측정하기 전에는 300건도 확정 납기로 취급하지 않는다.
- 모든 티켓의 담당자는 개발자 본인이다. 외부 법규 검토자가 확보되면 검토 범위와 시간을 별도로 편성한다. 개발자 검수를 전문가 인증으로 표시하지 않는다.

**계획 조정 원칙:** 품질 검사를 생략해 주차를 맞추지 않는다. 예비 시간을 넘으면 미완료 작업을 다음 스프린트로 이월하고, 의존 작업과 출시 목표일도 함께 이동한다. 8주가 고정이면 그 시점의 검증된 데모·실험 결과를 전달하고 미충족 출시 요건을 명시한다.

## 3. 스프린트 운영 규칙

- 티켓 상태는 `Backlog → Ready → In Progress → Review → Done`으로 관리하고, 진행 불가는 `Blocked`와 원인을 기록한다. 이 문서의 티켓은 모두 계획이며 완료된 작업이 아니다.
- 한 번에 주 작업 1개를 진행한다. 학습·다운로드 대기 중에는 독립적인 데이터 검수나 문서를 진행할 수 있지만, 이를 추가 인력의 작업량처럼 계산하지 않는다.
- `Ready`에는 필요한 입력·선행 결과·수용 기준이 있어야 한다. `Done`에는 산출물과 확인 결과가 있어야 한다. 관련 검사를 실행하지 못한 작업은 완료로 표시하지 않는다.
- 버그 수정과 검증은 각 티켓에 포함한다. 인용·시점·개인정보·평가 누출·갱신 복구 문제는 시연 전에 해결하거나 해당 기능을 보류한다.
- 스프린트 종료 때 목표 데모, 실제 투입 시간, 실패 사례, 다음 작업의 예상 시간을 기록한다. 기능 수 대신 수용 기준 충족 여부로 진척을 판단한다.
- 아래 시간은 초기 추정이다. 개별 작업이 커지면 완료 조건을 유지하면서 더 작은 티켓으로 나누고 합계와 후속 일정을 갱신한다.

### 선택 실험 S2-W01 — Wiki 검색 보조

2026-09-23 추가. 프로젝트 개발 Wiki와 구조 검사 도구를 도입하고, [오프라인 후보 검색·개발 비교 도구](wiki_retrieval.md)를 구현했다. 상태는 In Progress다. 실제 법규 Wiki 생성·검수·RAG 비교와 서비스 연결은 미완료이며 G1/G2 또는 S2-01 완료를 뜻하지 않는다. [도입 설계](llm_wiki.md)를 따른다.

선행 조건은 S2-01·03·06의 원문 검색·검증·개발 기준선이다. 법규 Wiki의 출처·스냅샷·검수 상태, 원문 변경 시 무효화, 후보 ID의 원문 재조회와 Wiki 장애 시 원문 검색 유지 경로를 구현한 뒤 `RAG`와 `RAG + Wiki 후보 확장`을 비교한다. 최종 평가 질문·정답·해설은 입력에서 제외한다.

완료 조건은 고정한 개발 평가에서 Recall@5·다중 조문/예외 누락·정합성·인용·시점·보류·지연·구축/갱신 비용을 기록하고 채택/보류 판단을 남기는 것이다. 실험 시작 전에 예산·허용 지연을 확정한다. 기존 34h와 P0 필수 일정에는 포함하지 않고 시작 시 추가 작업량을 재산정한다. E2/E4의 동일 검색 조건은 유지한다.

## 8. 데이터 검수와 평가에 대한 용량 점검

일정을 가장 크게 바꿀 수 있는 작업은 법규 예제 작성·검수와 생성 답변의 의미 평가다. 다음 숫자는 가능한 속도의 보증이 아니라 **시간 예산이 요구하는 처리량을 확인하기 위한 계산**이다.

| 작업 | 편성 예산 | 계산상 평균 | 측정·조정 시점 |
| --- | ---: | --- | --- |
| 학습 300건 작성·검수 | S3-01의 14h | 수정·중복 확인을 포함해 약 2.8분/건이어야 맞음 | S1-05에서 초안 작성부터 완료 검수까지 측정하고 S2 종료 때 재산정 |
| 최종 E1~E4 400개 출력 검사·채점 | S4-02의 16h | 실행 관리·정리 포함 약 2.4분/출력이어야 맞음 | S2-06에서 원출력·전달 출력의 주장 검수까지 측정 |

예를 들어 학습 예제 1건에 실제 5분이 걸리면 300건에 25시간이 필요해 해당 티켓이 11시간 초과한다. 이 경우 예비 시간을 사용한 뒤 남은 작업을 이월한다. 검수를 줄이거나 같은 사례의 패러프레이즈로 목표 건수만 채우지 않는다.

최종 평가의 시점 문항 15건에 실제 공식 자료를 확보하지 못하면 준비 미완료다. 가상 규정 테스트로 대체한 뒤 실제 법규 평가를 완료했다고 표시하지 않는다. 불확실한 해석 문항은 확인할 조건과 보류 기대 상태를 검수 단계에서 정의한다.

## 9. 출시 기준과 확인 시점

다음은 PRD 12절의 잠정 목표를 일정에 연결한 것이다. 정합성·의미적 근거 일치는 사람 검수 대상이며 인용 문자열 일치 검사로 대체하지 않는다.

| 기준 | 목표 | 증거를 남길 작업 |
| --- | --- | --- |
| 근거 검색 Recall@5 | 90% 이상 | S4-02, 검색 결과와 정답 근거 매핑 |
| 답변 정합성 | 답변 가능 문항 기준 85% 이상, 부당한 보류도 실패 | S4-02, 문항별 핵심 결론·조건·예외 검수 |
| 주장별 근거 일치율 | 95% 이상 | S4-02, 주장별 인용의 의미적 뒷받침 검수 |
| 허위·불일치 인용 | 최종 전달 답변에서 0건 | S4-02, ID·버전·발췌 검사 |
| 시점 오류 | 검증된 시점 문항에서 0건 | S4-02, 버전·적용 조건 검수 |

| E4 채택 | 위 품질 기준 충족 및 E2 대비 정합성·인용·시점 비악화 | S4-03, 동일 조건 비교와 채택 판단 |
| 응답 시간 | 단일 동시 요청 p95 30초 이내를 초기 목표로 두고 장비 실측으로 확정 | S1-04의 잠정 측정, S4-05의 전체 경로 측정 |

평가 전에 분모·집계 방법·실패 기준·응답 시간 측정 조건을 고정한다. 예를 들어 검색 Recall@5는 답변 가능 질문별 정답 근거 중 상위 5개에 포함된 비율을 구한 뒤 평균한다. 근거가 필요 없는 범위 밖 질문을 검색 성공 분모에 섞지 않는다. 실측하지 않은 지표나 확인하지 못한 사례를 통과로 처리하지 않는다.

평가셋 오류 0건은 해당 평가 범위의 결과다. 금융기관 도입 적합성 인증이나 전체 서비스의 무오류 보장으로 표현하지 않는다.

## 12. 이번 8주에서 미루는 작업

추가 금융 도메인, 전체 과거 시점, 정기 갱신 스케줄러, 개정 비교 UI, 사용자 이력·회원 기능, 관리자 화면, Spring Boot·별도 TypeScript UI, RAFT·CPT·GraphRAG, 대규모 모델 비교는 후속 작업으로 둔다. reranker와 고성능 추론 엔진은 측정한 검색·지연 문제가 있을 때 검토한다.

시점·인용 검사, 원문 문맥, 개인정보 기본값, 데이터 분리, 자체 학습 비교, 관리자 인증, 장애·갱신 복구는 P0의 완료 조건으로 유지한다. 필요한 정의·위임·부칙·별표를 빼서 도메인 범위를 줄이지 않는다.

## 13. 산출물 보관과 첫 착수 순서

아래 경로는 향후 작업의 보관 위치 제안이며 아직 생성된 산출물 목록이 아니다. 실제 코드 구조가 정해지면 경로를 조정하되 manifest와 보고서에서 서로 추적 가능하게 한다.

| 위치 제안 | 보관할 내용 | 생성 단계 |
| --- | --- | --- |
| `docs/decisions.md` | 범위·장비·모델·검수 방식·목표 변경 결정 | S1부터 갱신 |
| `data/manifests/` | 출처·스냅샷·데이터 분할·내용 해시 | S1부터 갱신 |
| `configs/` | 수집·검색·모델·학습·평가 설정 | S1~S3 |
| `reports/baseline/` | E1/E2 개발 평가와 오류 분석 | S2 |
| `reports/training/` | 학습 설정·자원·어댑터·개발 비교 | S3 |
| `reports/final/` | 봉인 세트 평가·실패 사례·채택 판단·과업 기록 | S4 |
| `docs/runbook.md`, `docs/api.md` | 실행·수집·복구 안내와 API 계약 | S4 |
| `docs/model_card.md`, `docs/data_card.md` | 모델·데이터 범위, 출처·라이선스·평가 한계 | S4 |

원문·가중치·대용량 출력은 지정 저장소에 보관할 수 있다. Git에는 필요한 코드·설정·manifest·검수 가능한 보고서를 남기고, 접근에 필요한 비밀값은 넣지 않는다. 최종 평가 파일은 별도 경로·접근 기록으로 관리해 학습 스크립트의 입력 탐색에 섞이지 않게 한다.

**첫 착수는 S1-01부터 한다.** 첫 9시간은 범위·미확정 결정 기록(2h), 개발 환경(3h), 공식 원문 확보와 누락 목록(4h)에 배정한다. 이후 자체 모델 실행과 초기 20문항 검수를 진행하고, 실제 자료 구조를 확인한 뒤 스키마를 확정한다. 법규 내용·최신 버전·모델 라이선스는 해당 작업 시점에 공식 자료로 확인한다.
