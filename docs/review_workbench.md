# 로컬 개발 문항 검수 화면

개발 문항·답변 초안과 인용 원문·부모 조문·시점 상태·미해결 참조·별표 PDF를 함께 보는 오프라인 화면이다. 별도 웹 서버나 외부 API 없이 HTML 파일을 브라우저에서 연다. [검수 정책](review_policy.md)의 존재·의미·시점·완전성 결과를 작성하고 기존 검수 등록 형식의 JSON을 저장한다.

## 현재 PC에서 열기

[개발 50문항 검수 화면](../artifacts/review-workbench/development-20260923/index.html)을 연다. 현재 묶음은 개발 50문항, 근거 연결 86건, 로컬 별표 PDF 11개를 포함한다. 근거 연결 수는 고유 조문 수와 다르다. 초기 20문항은 50문항에 포함되어 있다.

이 경로는 현재 PC에서 생성한 산출물이며 Git에 포함하지 않는다. 다른 환경에서는 원문·DB를 준비하고 아래 명령으로 새 폴더에 생성한다.

```powershell
# DB가 중지되어 있을 때만 실행
uv run --frozen python scripts/dev_db.py start
uv run --frozen python scripts/prepare_review_workbench.py --dataset s1-initial-20-v1 --dataset s1-evaluation-dev-v1 --output artifacts/review-workbench/development-new
```

이미 있는 출력 폴더는 덮어쓰지 않는다. 문항이나 원문이 바뀌면 새 폴더에 새 묶음을 만들고 새 버전을 검수한다. 서로 다른 묶음의 작성 중 파일은 섞지 않는다.

## 작성과 등록

1. 상단에서 문항을 선택하고 질문·사실관계·답변 초안과 원문을 대조한다. 원문 문자열 일치는 자동 검사 결과이며 의미·시점·완전성 통과를 뜻하지 않는다. 필요한 부모 조문과 별표를 펼쳐 읽고 공식 링크에서 문서 성격·버전·적용 조건을 확인한다.
2. 검수자·역할·방법·실제 검수 일시·소요 시간을 입력한다. 네 항목의 결과와 이유를 작성한다. 미확인 항목은 미검토 또는 판단 불확실로 남긴다. 검수 시각은 PC의 현지 시간으로 입력하고 내보낼 때 UTC 시각으로 변환한다.
3. 실제 대조한 공식 FAQ·해석자료를 JSON 배열로 기록한다. 개발자 검수에서 대조 자료가 없으면 네 항목이 모두 통과해도 등록 결과는 `needs_review`다. 확정할 수 없어 평가에서 제외할 문항은 제외 사유를 적는다.
4. 작업을 중단할 때 **작성 중인 내용 저장**으로 저장한다. 새로 열었을 때 **저장한 내용 불러오기**로 이어서 작성한다. 브라우저 저장소나 서버에 자동 저장하지 않으므로 다운로드가 완료되었는지 확인한다. 다른 리비전·원문·검수 상태의 묶음이나 작성 중 내용과 충돌하는 파일은 거절한다.
5. 실제 수행한 검수임을 확인하고 **현재 문항의 검수 JSON 저장**을 누른다. 검수자·일시·소요 시간·네 항목 사유·본인 확인이 없으면 내보내지 않는다. 발췌 불일치나 근거 미확보 상태에서는 존재 항목의 통과를 거절한다.
6. 다운로드한 `review-문항ID-r리비전.json`을 `data/review/submissions/`로 옮긴 뒤 등록한다. 작성 중 저장 파일은 등록용 파일과 형식이 다르다.

```powershell
uv run --frozen python scripts/review_dataset.py check-reviews data/review/submissions/검수파일.json
uv run --frozen python scripts/review_dataset.py import-reviews data/review/submissions/검수파일.json --attest-human-review
uv run --frozen python scripts/review_dataset.py status
```

화면은 DB를 변경하지 않는다. 등록 명령이 현재 리비전·내용 해시·근거를 다시 확인한다. 문항이 수정되었으면 기존 화면에서 작성한 기록은 거절되므로 새 묶음으로 다시 검수한다. 이 경로는 로컬의 명시적 검수 등록 도구이며 검수자의 신원을 인증하지 않는다.

## 등록 전 사전 점검

`check-reviews`는 기존 DB에서 읽기 전용 반복 읽기 트랜잭션으로 검사하며 마이그레이션이나 검수 기록을 쓰지 않는다. 단일 검수 객체 또는 비어 있지 않은 배열을 받고, 작성 중 저장 파일은 거절한다. 개발·학습 문항만 허용하며 최종 평가 문항의 본문은 읽지 않는다.

결과는 파일 내 순번(1부터), 오류 코드, 주의 사항과 `predicted_status`로 표시한다. 중복 문항, 현재 리비전·해시 불일치, 근거 ID 누락·중복, 존재 통과 시 원문 발췌 불일치를 확인한다. 질문·답변·검수 사유·검수자 정보는 보고서에 출력하지 않는다. 오류가 없으면 종료 코드 0, 입력 오류가 있으면 2다. `valid=true`는 등록 형식·참조 검사 통과이며 법률상 정합성이나 사람 검수의 진위를 보증하지 않는다.

네 항목이 모두 통과하고 외부 검수 또는 개발자의 공식 교차 대조가 있으면 예상 상태가 `reviewed`다. 미통과 항목이나 개발자 교차 대조 누락은 `needs_review`, 제외 사유가 있으면 `excluded`다. 등록 가능한 `needs_review` 기록도 종료 코드 0이므로 예상 상태를 함께 확인한다. 사전 점검 이후 DB가 바뀔 수 있어 실제 등록 시에도 재검사한다. 사전 점검은 등록 명령의 사람 검수 확인 옵션을 대체하지 않는다.

2026-09-24 사전 점검 추가 후 전체 86개 테스트가 통과했다. 가상 데이터에서 예상 상태와 실제 DB 등록 결과 일치, 미등록 상태 유지, 오래된 검수·중복·근거 불일치 거절을 확인했다.

## 자료 경계와 무결성

- 선택한 데이터셋 중 DB의 `split='dev'` 문항만 읽는다. 최종 평가 문항을 조회하는 옵션이나 디렉터리 전체를 수집하는 기능은 없다. 평가 내용이 들어 있는 HTML·JSON을 프로젝트 Wiki나 검색 인덱스에 넣지 않는다.
- 생성 시 읽기 전용 반복 읽기 트랜잭션으로 문항·근거 버전을 고정한다. HTML 원본 바이트의 해시를 확인하고 재파싱하여 조문의 본문·위치·조 번호·부모를 DB와 대조한다. 일치하지 않으면 생성을 중단한다.
- 보관 PDF의 해시를 검사해 묶음 안에 복사한다. 미확보·손상된 첨부는 해당 상태로 남기며 검토 완료로 표시하지 않는다. PDF 목록은 버전 전체의 첨부이며 질문과의 관련성을 자동 판정하지 않는다.
- 원문과 질문은 브라우저에서 텍스트로 표시한다. 외부 스크립트·네트워크 요청을 사용하지 않는다. 공식 출처와 로컬 PDF는 사람이 링크를 눌러 연다.
- `bundle.json`은 자료 사본, `index.html`은 화면, `assets/`는 PDF, `manifest.json`은 생성 결과와 파일 해시다. 작성 중 파일에는 입력한 검수자 정보가 포함될 수 있으므로 공유 범위를 구분한다.

## 검증과 다음 조건

2026-09-24 기준 전체 73개 테스트가 통과했다. 테스트 DB의 격리 스키마에서 원문 변조 거절, 최신 리비전, 최종 평가 제외, HTML 삽입 방지, 첨부 무결성, 경로 제한과 덮어쓰기 거절을 확인했다. Edge에서 문항 이동·저장·복원·버전 불일치 거절·내보내기를 실행했고, 가상 내보내기 결과를 `HumanReview`로 검증했다. 실제 사람 검수 기록은 생성하거나 등록하지 않았다.

이 화면은 개발 문항 검수를 돕는 단계다. 법규 조문별 적용 기간·경과조치·미해결 참조를 확정하고 스냅샷을 검증·활성화하는 작업은 별도로 남아 있다. 문항 검수 통과만으로 원문 스냅샷이나 Wiki 검색을 활성화하지 않는다. 실제 검색 비교 조건은 [오프라인 Wiki 실험](wiki_retrieval.md)을 따른다.
