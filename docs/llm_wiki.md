# FinReg의 LLM Wiki 도입

확인일: 2026-09-23. 결정: **프로젝트 지식 Wiki는 도입하고, 법규 검색의 Wiki 보조는 비교 평가 후 결정한다.** 현재 사용자 질의 API와 RAG 기준선은 아직 구현 전이다.

## 판단 근거

[Karpathy의 LLM Wiki 제안](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)은 원본 자료, LLM이 유지하는 연결된 Markdown 페이지, 운영 규칙을 분리한다. 자료를 읽으며 요약·개념·관계를 축적하고 목차와 변경 로그를 유지하는 방식이다. 특정 모델이나 필수 설치 패키지를 뜻하지 않는다. [Microsoft의 구현](https://github.com/microsoft/llmwiki)은 이 방식을 VS Code 확장으로 제공한다.

FinReg에는 반복적으로 확인하는 설계 결정과 조문 간 문맥을 정리할 수 있다는 이점이 예상된다. 반면 요약 과정에서 예외가 빠지거나 개정 전후 조건이 섞일 수 있고, 새 원문을 수집할 때 파생 페이지도 갱신해야 한다. 이는 FinReg 요구사항에 따른 설계 판단이다. 위 제안과 구현 소개만으로 금융 법규 정확성·응답 속도 개선이 입증된 것은 아니다.

| 용도 | 이번 결정 | 이유 |
| --- | --- | --- |
| 개발 개념·결정 탐색 | 도입 | 여러 문서의 관계와 미완료 조건을 한 곳에서 찾을 수 있다. |
| 법규 근거 후보 확장 | 오프라인 실험 경로 구현 | 가상 규정으로 검증했다. 실제 품질 비교와 서비스 채택은 미완료다. |
| 최종 인용과 적용 판단 | 기존 원문 검증 유지 | 요약만으로 버전·발췌·기준일·경과조치를 확인할 수 없다. |
| 대화·평가 정답의 자동 축적 | 제외 | 개인정보 비저장과 최종 평가 분리 조건을 유지한다. |

추가 패키지·유료 API·벡터 DB를 설치하지 않았다. 초기 페이지는 기존 프로젝트 문서를 읽은 에이전트가 작성했으며 자동 수집 서비스나 법규 요약 모델을 실행한 결과가 아니다.

## 현재 사용 방법

[목차](../wiki/index.md) → 관련 개념 → 페이지의 출처 문서 순서로 읽는다. 운영 규칙은 [wiki/AGENTS.md](../wiki/AGENTS.md), 변경 이력은 [wiki/log.md](../wiki/log.md)에 있다. Wiki의 설명과 원본이 다르면 원본·실제 구현을 확인하고 Wiki를 수정한다.

```powershell
uv run --frozen python scripts/check_wiki.py
# 페이지를 원본과 대조한 뒤, manifest에 넣을 현재 해시 확인
uv run --frozen python scripts/check_wiki.py --source-hashes
```

검사기는 `wiki/manifest.json`에 등록된 프로젝트 문서만 읽는다. 허용 출처는 PRD·스프린트·결정·데이터 모델·수집 상태·검수 정책·Wiki 도입 및 검색 실험 문서로 제한한다. 데이터셋·원문 보관 폴더·비밀값은 입력 대상이 아니다. 경로 이탈과 심볼릭 링크를 거절한다. 평가 내용을 문서에 복사해 넣었는지는 자동 판정하지 못하므로 운영 규칙으로도 금지한다.

`sources`에는 경로와 SHA-256, `pages`에는 페이지 경로와 의존 출처를 기록한다. 해시는 UTF-8 텍스트의 CRLF/CR을 LF로 통일한 뒤 계산한다. 이는 개발 문서 변경 탐지용이며 법규 원본 바이트 해시와 구분한다. 검사기는 출처 변경, 등록 누락, 빈 페이지, 파일 링크 누락, 출처 의존성 누락, 목차에서 빠진 페이지를 오류로 보고하며 종료 코드 1을 반환한다. 자동 수정이나 자동 검수 승격은 하지 않는다.

파일 링크는 `[이름](상대경로.md)` 형식을 사용한다. 검사 범위는 이 형식의 파일 대상 존재 여부이며 헤딩 앵커·외부 URL의 가용성·주장 의미·법규 최신성은 검사하지 않는다. 코드 블록·인라인 코드의 예시는 검사에서 제외한다. 각 개념 페이지의 모든 직접 출처를 manifest에 등록한다. 개념끼리의 링크는 탐색용이며 다른 Wiki만을 근거로 결론을 확정하지 않는다.

출처가 바뀌면 의존 페이지를 원본과 대조하고 조건·예외·미완료 사항을 수정한다. 관련 페이지와 목차를 갱신하고 로그에 영향·남은 확인 사항을 추가한 뒤 해시를 갱신한다. 해시만 바꿔 오래된 요약을 최신으로 표시하지 않는다. 검사가 통과해도 사람의 법규 의미 검수가 완료된 것은 아니다.

## 법규 검색으로 확장할 때의 계약

[오프라인 검색 실험](wiki_retrieval.md)에 검증된 DB 스냅샷 로딩, 원문 BM25와 Wiki 후보 결합, 원문 재조회, 해시·시점·검수·문맥 검사, 개발 문항 전용 비교 경로를 구현했다. 아래 계약 중 실제 LLM 요약 생성, 서비스 검색 연동·갱신 활성화, 사용자 요청 추적은 미구현이다. 템플릿 생성은 요약이나 사람 검수를 대신하지 않는다.

1. 검증된 원문 스냅샷에서만 별도 법규 Wiki를 만든다. 페이지는 `page_id`, `snapshot_id`, `version_ids`, `provision_ids`, 원문 해시, `document_type`, `review_status`, 생성 모델·리비전·프롬프트·설정을 보존한다. 요약의 핵심 주장마다 원문 조문을 연결한다. 프로젝트 Wiki와 저장 위치·입력 목록을 분리한다.
2. AI가 생성한 설명은 초안이며 사람의 존재·의미·시점·완전성 검수를 자동 통과시키지 않는다. FAQ·해석자료와 법령을 구분하고, 미확보 정의·부칙·별표·충돌은 미해결로 남긴다.
3. Wiki는 검색어·관련 조문 ID 후보를 보탠다. 최종 문맥은 요청 시작에 고정한 스냅샷의 원문에서 다시 조회하고 기준일·종료 경계·경과조치·지원 범위를 검사한다. Wiki 문장을 인용 발췌로 넘기지 않는다.
4. 원문 버전·해시가 바뀌면 영향 페이지를 `stale`로 표시하고 후보 확장에서 제외한다. 새 페이지 검증 후 스냅샷과 함께 교체한다. Wiki 없음·갱신 실패·참조 불일치 때는 원문 검색을 유지한다. 원문 검색 장애는 기존 `system_error` 규칙으로 처리한다.
5. 요청 기록에는 Wiki 사용 여부·빌드 ID·선택 페이지 ID를 남기되 사용자 질문 원문을 저장하지 않는다. 재현 실험의 Wiki 빌드는 고정하며 최종 평가로 얻은 답을 다시 Wiki에 넣지 않는다.

## 후속 비교와 채택 조건

S2의 원문 검색·검증 기준선이 준비된 뒤 개발 평가에서 한 가지 변수만 바꾼다. 같은 모델 리비전·원문 스냅샷·문맥 예산·생성 설정·검증기를 사용해 `RAG`와 `RAG + Wiki 후보 확장`을 비교한다. E2/E4의 미세조정 효과 비교에서는 선택한 검색 문맥을 동일하게 유지한다.

- 질문별 원문 근거 Recall@5, 다중 조문·예외 누락과 유형별 실패를 기록한다.
- 답변 정합성·주장별 근거 일치·인용 오류·시점 오류·불필요한 보류가 기준선보다 악화되지 않아야 한다.
- 다중 조문 질문의 검색 재현율이나 예외 누락에서 관찰 가능한 개선이 있어야 한다. 표본 수를 명시하며 통계적 유의성을 임의로 주장하지 않는다.
- 응답 지연·입력 토큰·Wiki 생성 및 갱신 시간·저장량을 함께 측정한다. 실행 전 비교 예산과 허용 지연을 고정한다.
- 원문 개정, 오래된 페이지, 허위 조문 ID, 미검수 시점, 미확보 부칙, 자료 충돌, Wiki 장애, 평가 데이터 유입 차단 사례를 확인한다.

기준을 충족하지 않으면 프로젝트 지식 Wiki만 유지한다. 현재 완료된 것은 문서 Wiki·구조 검사와 오프라인 검색 실험 코드다. BM25와 Wiki 후보 확장을 가상 규정에서 검사했으며, 실제 RAG의 법규 답변 정확도·비용 절감은 측정하지 않았다. 관련 요구사항은 FR-03~07·10·12·13, NFR-01·06·08이다.
